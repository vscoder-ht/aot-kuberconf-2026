# Файловые capabilities

Кейс справочный, в показ не входит.

## Что проверяем

Три пода из образа `archlinux`: настоящие `arping`, `setcap`, `getcap`, `capsh` и полноценный `setpriv` из util-linux уже в образе, пакеты доустанавливать не нужно. Командой кейса служит `arping`: ему нужен сырой сокет, то есть `CAP_NET_RAW`. Ping не подходит: на узле `net.ipv4.ping_group_range` разрешает ping-сокеты любой группе, и ping работает даже без `NET_RAW`. Busybox не подходит: его апплеты — ссылки на общий `/bin/busybox`, атрибут ставился бы на все команды сразу, а busybox-версии `setpriv` не умеют снимать ограничивающий набор.

Порядок кейса:

| Pod | Capabilities | File capabilities до | File capabilities после | Проверка | Результат |
|---|---|---|---|---|---|
| `drop-pod` | `drop: [ALL]` | — | — | `arping` от root | `socket: Operation not permitted` |
| `no-drop-pod` | набор по умолчанию | — | `cap_net_raw=ep` | `arping` от uid 1000 | работает: право дал атрибут файла |
| `no-drop-pod`, контроль | набор по умолчанию | копия `/tmp/arping-copy` без атрибута | без атрибута | `arping-copy` от uid 1000 | `socket: Operation not permitted` |
| `no-drop-pod` | набор по умолчанию, затем `setpriv --bounding-set=-all` снимает все наборы | `cap_net_raw=ep` | `cap_net_raw=ep` | `arping` после снятия наборов | `execve` возвращает `EPERM`, файл не запускается |
| `add-pod` | `drop: [ALL]` + `add: [NET_RAW]` | — | — | `arping` от root | работает: право вернули в под, а не в файл |

Проверки против пустого ограничивающего набора выполняются в `no-drop-pod` вручную через `setpriv`: в поде с `drop: [ALL]` `setcap` не сработал бы — `SETFCAP` был бы снят, поэтому атрибут ставят до снятия наборов.

## Зачем

`setcap` работает в запущенном контейнере без `privileged`: право `SETFCAP` входит в набор среды выполнения по умолчанию. Файл с атрибутом `security.capability` выдаёт право процессу при `execve` — это замена setuid root на одно право. Строка `no-drop-pod` показывает это честно: у процесса от uid 1000 своих прав нет, единственный источник `NET_RAW` — атрибут файла.

Ограничение: атрибут не поднимает права выше ограничивающего набора контейнера (`CapBnd`). После `drop: [ALL]` этот набор пуст, и файл с атрибутом становится неисполняемым (последняя строка `no-drop-pod` в таблице).

## Выводы

Атрибут файла и набор пода — два источника одного права. Вместе они не обязательны.

Атрибут нужен процессу, у которого своего права нет. В `no-drop-pod` процесс от uid 1000 шёл с пустым эффективным набором, и `NET_RAW` ему дал только `cap_net_raw=ep`. Копия того же файла без атрибута от того же uid при наборе по умолчанию получила `socket: Operation not permitted`. Наличие `NET_RAW` в наборе по умолчанию этот отказ не снимает: набор по умолчанию право получает процесс root, а не процесс от uid 1000.

Процессу root атрибут не нужен, если `NET_RAW` уже есть в его наборе. Это записано на `add-pod`: после `drop: [ALL]` право возвращено через `add: [NET_RAW]`, атрибута на файле нет, `arping` от root проходит. От root на `no-drop-pod` до `setcap` команду не записывали. Набор по умолчанию содержит `NET_RAW`, поэтому для root на этом поде атрибут тоже не требуется.

Атрибут применяется, пока право остаётся в ограничивающем наборе пода. Его снимают `drop: [NET_RAW]` и `drop: [ALL]` без `add: [NET_RAW]`. `drop: [ALL]` с последующим `add: [NET_RAW]` возвращает право в ограничивающий набор, и атрибут в таком поде тоже применился бы. Пару «атрибут и `add-pod`» не запускали. Строку `drop: [NET_RAW]` отдельно не запускали.

Пустой ограничивающий набор против уже стоящего `cap_net_raw=ep` проверяли в `no-drop-pod` через `setpriv --bounding-set=-all`. Отдельный под с `drop: [ALL]` и заранее выставленным атрибутом не собирали: внутри него `setcap` не сработал бы, `SETFCAP` снят. Результат: `execve` возвращает `EPERM`, файл не запускается. Флаг `e` в `=ep` просит ядро поднять право файла в эффективный набор. Права нет в ограничивающем наборе, пересечение пустое, и ядро отказывается выполнять `execve`. До вызова сокета выполнение не доходит.

Поле `allowPrivilegeEscalation` в трёх подах не задано. Пустое поле оставляет `NoNewPrivs` равным 0, и ядро на `execve` применяет файловые capabilities. Прогон от uid 1000 это подтверждает: атрибут поднял `NET_RAW`. При значении `false` тот же атрибут право не поднимает. В этом кейсе поле не переключали.
