# Файл root и hostUsers: false

Прогон 22 ноября 2026 на k3s `v1.34.12+k3s1`. Вывод — [output.md](output.md). В показ не входит.

## Что проверяем

На узле в каталоге `/var/tmp/rootread` лежит файл `token` режима `0600`, владелец uid `0`. Под `rootfile-prep` создаёт этот файл от uid `0` без поля `hostUsers`. Секрета нет.

Два пода монтируют тот же каталог в `/data`. У обоих `hostUsers: false`.

`rootfile-userns0` запускается с `runAsUser: 0`.

`rootfile-userns1000` запускается с `runAsNonRoot: true` и `runAsUser: 1000`.

## Результат

Под `rootfile-userns0` команда `cat` выводит содержимое файла. Внутри `id` показывает uid `0`, `ls -ln` показывает владельца `0`. Файл `/proc/self/uid_map` содержит `0 1697579008 65536`: первое число — начало внутри контейнера, второе — начало на узле, третье — длина. Точка `/data` смонтирована с флагом `idmapped`.

Флаг `idmapped` ставит kubelet, когда у пода задано `hostUsers: false`. В манифесте этого флага нет.

Флаг относится к точке монтирования `/data`. Ядро через неё сопоставляет uid файла с uid процесса внутри пода. Номер владельца в записи на диске при этом не меняется.

Файл на диске принадлежит uid `0`. Внутри пода `ls` показывает того же владельца `0`, поэтому процесс с `runAsUser: 0` открывает файл режима `0600`. На узле этот процесс идёт от `1697579008`.

Под `rootfile-userns1000` видит того же владельца `0`. Команда `cat` возвращает `Permission denied`.

## Где запускать

Манифест рассчитан на k3s. На этом прогоне поды с `hostUsers: false` дошли до `Running`: ext4 принимает idmap. На управляемом кластере такой под до `Running` не доходит, snapshotter `overlayfs` idmap не поддерживает.
